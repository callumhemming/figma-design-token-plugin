# Todo / Ideas

## Tokens

- **Run a schema validator over token files.** We hand-validated `resolver.json` against the DTCG resolver schema with `ajv` (Draft-07, schema at `https://www.designtokens.org/schemas/2025.10/resolver.json`). Do the same for the token files themselves — the resolver schema's `$defs` embed the full `token.json`/`group.json`/`color.json` etc. definitions, so the same schema can validate token file contents too. Would have caught the invalid `#fnfnf` hex automatically instead of by eye. Candidate: an `npm run validate:tokens` script.
- **Per-brand semantic parity check, and its limits.** Each brand now owns its own semantic file (`brands/<brand>/semantic/color.json`) instead of one shared file, so brand-agnostic primitives (e.g. a plain `sunset-orange-1`) stay possible — the tradeoff is schema drift: add a semantic token for brand-a and nothing forces brand-b to define it too. The near-term fix is a validator that diffs each brand's semantic token *paths* against each other and fails if they don't match (extends the schema validator bullet above). But "every brand must expose the same semantic surface" is a policy of *this* project (single project, multiple brands that are meant to be interchangeable) — it shouldn't be baked into `resolve.ts`/`flatten.ts` as a universal rule. If this ever supports switching between different *projects* (not just brands within one project), those projects may not share a `brand` axis at all, or may legitimately want different token categories/types per project. Worth designing the parity check as project-level config (which token set is "required," which axis it's checked across) rather than a hardcoded brand-vs-brand diff, so it's swappable per project later.
- **Fix `brands/acme/primitives/color.json` → `color.brand.300`** — currently `"#fnfnf"`, not a valid hex color (`n` isn't a hex digit). Still unresolved.
- **Globex is a placeholder brand.** Added to demonstrate/test brand-toggling — its palette (`brands/globex/primitives/color.json`, orange/purple/gray) is made up, not real brand colors. Replace or remove once there's an actual second brand.
- **Real dark-mode primitives.** `global/semantic/color.dark.json` currently reuses light-mode primitives (`brand.200`, `grey.500`) as placeholders, flagged via `$description`. Needs its own dark-appropriate primitive palette.
- **`$type` inheritance from parent groups.** Spec allows a token to omit `$type` and inherit it from the nearest parent group that declares one. `flattenTokens`/`isLeaf` don't implement this — harmless today since every leaf sets `$type` explicitly, but would silently produce `type: undefined` if that ever changes.
- **Cycle detection in `resolveValue`.** A circular alias chain (`{a}` → `{b}` → `{a}`) recurses until the stack overflows. No guard in place; not an issue with current data.
- ~~`resolveValue` can't resolve per-property aliases inside composite `$value`s.~~ Done — `resolveValue` in `flatten.ts` now recurses into arrays and objects, resolving each sub-property independently (not just a top-level alias string). Covers `typography`, `border`, `shadow`, `gradient`, `transition`.
- **Confirm the DTCG `typography` composite's real sub-properties.** Used `fontFamily`/`fontSize`/`fontWeight`/`lineHeight` as the obvious set when scaffolding `global/semantic/typography.json`, but didn't get a confirmed exact list from the spec (content was truncated when fetched) — worth double-checking against the Format module before treating this as final.
- **No per-type editors beyond color.** `TokenChip` only builds an edit UI (hex input, swatch, `{ref}` picker) for `$type: "color"` — every other type (`dimension`, `typography`, `border`, `shadow`, ...) renders read-only via `formatResolvedValue`. Extending this would use `COMPOSITE_TOKEN_SHAPES` (already declares each composite's named sub-properties and their expected reference type) to drive a per-field form, the way the color editor's `referencePaths` picker works today.
- **Filter the token edit modal's left-hand column to slot-compatible tokens.** Currently `TokenEditModal.tsx` (lines 43-66) always lists *every* token of *every* primitive type via `PRIMITIVE_TOKEN_TYPES`, regardless of what's selected on the right — the chip `onClick` is even still a no-op (`() => {}`, line 59). When editing a composite token (or any token), the list should instead narrow to just the tokens that fit the currently-selected slot's expected type. The mechanism already exists: `referencePaths(tree, type?)` in `flatten.ts` (lines 173-183) filters flattened tokens down to one `$type`, and `COMPOSITE_TOKEN_SHAPES` (lines 191-224) already declares each composite sub-property's `expectedType` (e.g. `typography.fontSize` → `dimension`) — it's the same pairing the color editor's `{ref}` picker uses today, just not wired up here yet. Also relevant to `TypographyEdit.tsx`, whose per-sub-property pickers are currently hardcoded single chips (`PLACEHOLDER_PATHS`) rather than an actual filtered, selectable list.
- **`gradient` doesn't fit `COMPOSITE_TOKEN_SHAPES`.** Its `$value` is an array of `{ color, position }` stops, not a flat object of named sub-properties like every other composite — so it's excluded from the map that would drive a per-field editor. Would need its own array-shaped editor treatment.
- **Storybook write-back mock, deferred until editing is more robust.** Read side is mocked via `staticDirs` (GET only — see the Resolver section below). The reverse — actually persisting a `setTokenValue` edit to `src/tokens/*.json` on disk — needs a dev-only Vite middleware registered in `.storybook/main.ts`'s `viteFinal` (a `configureServer` hook handling `POST /tokens/<ref>` and writing the body to the matching file), plus a client-side `saveTokenSource(baseUrl, ref, tree)` mirroring `fetchTokenRegistry`. Only works under `storybook dev` (a real Node process is running) — `build-storybook`'s static output has no server to accept the POST. Open question before wiring it up: debounce/explicit-save vs. write-on-every-keystroke, to avoid thrashing the file and retriggering Vite's watcher/HMR loop.

## Resolver

- ~~Build the actual resolver-consumer.~~ Done — `resolve.ts`'s `resolveTokens(resolverDoc, input, registry)` walks `resolutionOrder`, resolves each modifier's context (input value, or its `default`), and folds through `mergeTokenTrees`. `TokensContextProvider` calls it fresh on every render for the *active* theme x brand only — no precomputed permutation cross product, so this isn't a combinatorial-growth concern the way it would be if every permutation were precomputed eagerly.
- ~~Loading is still static imports, not runtime-fetched.~~ Partially done — `resolve.ts`'s `fetchTokenRegistry(baseUrl)` fetches `resolver.json`, walks it via `collectSourceRefs` to find every source `$ref`, and fetches each one, replacing the old static-import registry entirely (`TokensContextProvider` has no JSON imports left). **But** this is currently mocked: `TOKENS_BASE_URL` in `TokensContextProvider.tsx` points at `/tokens`, served by Storybook's `staticDirs` (`.storybook/main.ts`) from local `src/tokens/`, not a real GitHub repo. Real remaining work: (1) point `TOKENS_BASE_URL` at an actual `raw.githubusercontent.com` (or similar) URL, (2) add that domain to `manifest.json`'s `networkAccess.allowedDomains` (currently `["none"]`) so the real Figma plugin build can fetch it too — until then, `ui.tsx`'s build has no server to fetch `/tokens` from and won't load tokens outside Storybook.
- **Branch selection for `TOKENS_BASE_URL` doesn't need a real git engine.** Toyed with running git client-side (e.g. `isomorphic-git`) so users could pick which branch of the token repo to pull from, but GitHub's raw/API endpoints already take a branch as a URL param — `raw.githubusercontent.com/<org>/<repo>/<branch>/...` or the Contents API's `?ref=<branch>` — so "pick a branch" is just another value fed into the existing `fetchTokenRegistry(baseUrl)`, not a new dependency. Only reach for something like `isomorphic-git`/`wasm-git` if we actually need git operations (diff, merge, commit) client-side, not just reading files at a ref. Same `manifest.json` `networkAccess.allowedDomains` blocker as the bullet above applies either way.

## Ideas

- **Utopia support** — fluid type/space scales (utopia.fyi, `clamp()`-based) as a token source, instead of fixed step values.
- **Default/baseline token set** — commonly-needed tokens we don't have yet: text (font family/size/weight/line-height scale), and basic component-level tokens (button padding, radius, etc.) beyond raw color primitives.
- **Radix support** — likely Radix Colors (matched 12-step light/dark scales) as a primitive palette source; possibly also Radix UI component theming compatibility.
- **Auto dark/light mode** — follow the system/Figma appearance setting automatically for the `theme` modifier instead of a manual toggle.
- **Generate CSS on the fly with Style Dictionary, to retheme the plugin's own UI from its own UI.** Goal: instead of (or alongside) the current React-context-driven resolution, produce actual CSS (custom properties) from the resolved token tree at runtime and apply it live, so the plugin dogfoods its own token system for its own styling. Style Dictionary v4 was rewritten to ESM specifically to be browser-native, not Node-only (confirmed against `styledictionary.com/versions/v4/migration/`; there's a live example at `style-dictionary-play.dev`). Catch: the CLI's disk-based file I/O (read token files, write platform output files) doesn't apply in-browser — you'd skip the file-reading step and hand it already-resolved token data as JS objects directly, then use a format/handler that returns a CSS string for us to inject (e.g. onto `:root` or a `<style>` tag) instead of writing to disk. Open question before starting: does Style Dictionary replace `resolve.ts`'s alias-resolution work, or just sit downstream of it as the CSS-var formatting step, since `resolveTokens` already produces fully-resolved values per brand/theme? Leaning toward the latter — Style Dictionary's value here is its output-format layer (CSS vars now, other platforms free later), not redoing resolution we already have.

## Plugin → repo sync

- **Sync edits made in the Figma plugin back into the source JSON files.** Plan from earlier discussion: stamp provenance (`{ file: "<source path>" }`) onto each token **in memory** at flatten time, per source file, before merging — not persisted into the JSON files, since it's derivable from which file you're reading and would go stale if files get renamed/moved. Survives `mergeTokenTrees` for free, since conflict resolution there copies the whole winning leaf object.
- **Open product question, not yet decided:** when someone edits a token whose value came from resolving an alias (e.g. `text.secondary` → `{color.grey.500}`), does the edit change the alias's *target* (`grey.500`, affecting everything else referencing it) or snap `text.secondary` to a literal value and break the alias? Needs a decision before the write-back path can be designed.
